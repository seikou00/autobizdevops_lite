# 增量实现

## 使用申明
- 当前agent_team模式下git worktree无法使用，禁止任务并行
- 当前agent_team模式下git commit无法使用，不用提交代码

## 技能状态维护


> 使用脚本更新技能执行状态

- 技能开始执行
```
python "${pluginPath}/hooks/update_state.py" --feature "${feature}" --checkpoint code_in_progress
```
- 技能执行完成后
```
python "${pluginPath}/hooks/update_state.py" --feature "${feature}" --checkpoint code_done
```


## 概述

将 `FEATURE_DIR/plan.md` 以薄的垂直切片构建——实现一个片段，测试它，验证它，然后扩展。避免一次性实现整个功能。每个增量都应该让系统处于可工作、可测试的状态。这是让大型功能可管理的执行纪律。

## 何时使用

- 实现任何多文件变更
- 从任务分解中构建新功能
- 重构现有代码
- 任何你忍不住在测试前写超过约 100 行代码的时候

**何时不使用：** 范围已经最小化的单文件、单函数变更。

## 增量周期

```
┌──────────────────────────────────────┐
│                                      │
│   实现 ──→ 测试 ──→ 验证 ──┐        │
│       ▲                    │        │
│       └───── 提交 ◄────────┘        │
│              │                       │
│              ▼                       │
│          下一个切片                   │
│                                      │
└──────────────────────────────────────┘
```

对于每个切片：

1. **实现** 最小完整的功能片段
2. **测试** —— 运行测试套件（或如果不存在则编写一个测试）
3. **验证** —— 确认切片按预期工作（测试通过、构建成功、手动检查）
4. **提交** —— 用描述性消息保存你的进度(当前agent_team模式下git commit暂不可用，无需提交)
5. **移动到下一个切片** —— 继续推进，不要重新开始

## 切片策略

### 垂直切片（首选）

构建一条穿过整个栈的完整路径：

```
切片 1：创建任务（数据库 + API + 基础 UI）
    → 测试通过，用户可以通过 UI 创建任务

切片 2：列出任务（查询 + API + UI）
    → 测试通过，用户可以看到他们的任务

切片 3：编辑任务（更新 + API + UI）
    → 测试通过，用户可以修改任务

切片 4：删除任务（删除 + API + UI + 确认）
    → 测试通过，完整的 CRUD
```

每个切片都交付可工作的端到端功能。

### 契约优先切片

当后端和前端需要并行开发时：

```
切片 0：定义 API 契约（类型、接口、OpenAPI 规范）
切片 1a：针对契约实现后端 + API 测试
切片 1b：针对匹配契约的模拟数据实现前端
切片 2：集成并进行端到端测试
```

### 风险优先切片

首先处理最冒险或最不确定的部分：

```
切片 1：证明 WebSocket 连接有效（最高风险）
切片 2：在已验证的连接上构建实时任务更新
切片 3：添加离线支持和重连
```

如果切片 1 失败，你在投入切片 2 和 3 之前就发现了。

## 实现规则

### 规则 0：简洁优先

在写任何代码之前，问："能工作的最简单的东西是什么？"

写完代码后，对照这些检查进行审查：
- 这能用更少的行数完成吗？
- 这些抽象配得上它们的复杂性吗？
- 一个资深工程师看了会想说"你为什么不直接……"？
- 我是在为假设的未来需求构建，还是为当前任务构建？

```
简洁性检查：
✗ 一个通知就用上通用 EventBus 加中间件管道
✓ 简单的函数调用

✗ 两个相似组件就用抽象工厂模式
✓ 两个简单的组件加共享工具函数

✗ 三个表单就用配置驱动的表单构建器
✓ 三个表单组件
```

三行相似的代码比一个过早的抽象更好。先实现朴素、明显正确的版本。只有在测试证明了正确性之后才优化。

### 规则 0.5：范围纪律

只碰任务要求的内容。

不要：
- "清理"你变更旁边的代码
- 重构你没修改的文件中的导入
- 删除你不完全理解的注释
- 添加不在规格中因为"看起来有用"的功能
- 在你只读的文件中现代化语法

如果你注意到任务范围外值得改进的地方，记下来——不要修复它：

```
注意到但没有碰：
- src/utils/format.ts 有一个未使用的导入（与此任务无关）
- 认证中间件可以用更好的错误消息（单独的任务）
→ 需要我为这些创建任务吗？
```

### 规则 1：一次只做一件事

每个增量改变一个逻辑上的东西。不要混用关注点：

**不好：** 一个提交添加新组件、重构现有组件并更新构建配置。

**好：** 三个单独的提交——每次变更一个。

### 规则 2：保持可编译

每个增量之后，项目必须构建，现有测试必须通过。不要在切片之间让代码库处于损坏状态。

### 规则 3：为不完整功能使用功能开关

如果一个功能还没准备好给用户，但你需要合并增量：

```typescript
// 工作进度的功能开关
const ENABLE_TASK_SHARING = process.env.FEATURE_TASK_SHARING === 'true';

if (ENABLE_TASK_SHARING) {
  // 新的分享 UI
}
```

这让你可以将小增量合并到主分支，而不暴露未完成的工作。

### 规则 4：安全默认值

新代码应该默认安全、保守：

```typescript
// 安全：默认禁用，选择加入
export function createTask(data: TaskInput, options?: { notify?: boolean }) {
  const shouldNotify = options?.notify ?? false;
  // ...
}
```

### 规则 5：易于回滚

每个增量应该可以独立回退：

- 增量式变更（新文件、新函数）容易回退
- 对现有代码的修改应该最小且聚焦
- 数据库迁移应该有对应的回滚迁移
- 避免在一个提交中删除某物并在同一提交中替换它——分开它们

## 与 Agent 协作

- 当指导 Agent 增量实现时：

```
"让我们实现计划中的任务 3。

先从数据库 schema 变更和 API 端点开始。
暂时不要碰 UI —— 我们在下一个增量中做。

实现后，运行 `npm test` 和 `npm run build` 来验证
没有破坏任何东西。"
```
明确每个增量的范围内和范围外内容。



## 增量检查清单

每个增量之后，验证：

- [ ] 变更做了一件事并且做完整了
- [ ] 所有现有测试仍然通过（`npm test`）
- [ ] 构建成功（`npm run build`）
- [ ] 类型检查通过（`npx tsc --noEmit`）
- [ ] 代码检查通过（`npm run lint`）
- [ ] 新功能按预期工作
- [ ] 变更已提交并附有描述性消息

## 常见借口

| 借口 | 现实 |
|---|---|
| "我最后一起测试" | Bug 会复合。切片 1 的 bug 会让切片 2-5 都错。每个切片都要测试。 |
| "一次性做更快" | 它*感觉*更快，直到某些东西坏了，你无法找出 500 行变更中的哪一行导致的。 |
| "这些变更太小，不值得单独提交" | 小提交是免费的。大提交隐藏 bug 并让回退痛苦。 |
| "我稍后添加功能开关" | 如果功能不完整，它不应该对用户可见。现在就添加开关。 |
| "这个重构够小，可以包含" | 重构与功能混在一起让两者都更难审查和调试。分开它们。 |

## 危险信号
- 写超过 100 行代码而没有运行测试
- 一个增量中有多个无关的变更
- "我就快速把这个也加上"的范围扩张
- 为了更快推进而跳过测试/验证步骤
- 增量之间构建或测试损坏
- 积累大量未提交的变更
- 在第三个用例需要之前就构建抽象
- "既然我在这里"就碰任务范围外的文件
- 为一次性操作创建新的工具文件


## 验证清单

完成一个任务的所有增量后：

- [ ] 每个增量都经过了单独测试和提交
- [ ] 完整测试套件通过
- [ ] 构建干净
- [ ] 功能端到端按规格工作
- [ ] 没有未提交的变更残留
